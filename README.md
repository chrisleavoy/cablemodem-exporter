# cablemodem-exporter

Prometheus exporter, Grafana dashboard and reboot tool for Compal/CBN DOCSIS 3.1 cable modems:
per-channel SNR, power and lock state, upstream transmit power, modem status, and the modem's
event log.

## Supported hardware

| Model | Firmware | Status |
|-------|----------|--------|
| Compal/CBN CD8000 | CD8000-7.13.198.12-NOSH | Tested (`tests/fixtures` captured from it) |

Other CBN firmware that serves `/xml/getter.xml` may work. If a response doesn't match what the
exporter expects, polls fail with `cablemodem_poll_errors_total{kind="protocol"}` rather than
publishing wrong numbers.

## Install

Requires Python 3.10+ and a host on the modem's LAN segment (the modem is usually 192.168.100.1).

```bash
git clone https://github.com/chrisleavoy/cablemodem-exporter.git && cd cablemodem-exporter
sudo useradd --system --no-create-home --shell /usr/sbin/nologin cablemodem-exporter
sudo python3 -m venv /opt/cablemodem-exporter/venv
sudo /opt/cablemodem-exporter/venv/bin/pip install .
sudo install -d -m 0755 /etc/cablemodem-exporter
sudo install -m 0600 cablemodem-exporter.env.example /etc/cablemodem-exporter/env
sudoedit /etc/cablemodem-exporter/env          # set CM_PASSWORD
sudo install -m 0644 cablemodem-exporter.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cablemodem-exporter
curl -s localhost:9884/metrics | grep cablemodem_up
```

The unit's `StateDirectory=cablemodem` creates `/var/lib/cablemodem`, owned by the service user,
which holds a copy of the modem's event log so restarts don't report old entries again.

### Prometheus

```yaml
scrape_configs:
  - job_name: cablemodem
    scrape_interval: 30s
    static_configs:
      - targets: ["localhost:9884"]
```

The exporter polls the modem on its own timer (`CM_POLL_INTERVAL`) and scrapes return the latest
poll immediately, so the scrape interval and timeout don't need to account for the modem.

A stuck poll leaves the last successful readings in place, so alert on their age. That only works
while the exporter is running, so also alert on the scrape target itself (adjust the job name):

```yaml
groups:
  - name: cablemodem
    rules:
      - alert: CableModemExporterDown
        expr: up{job="cablemodem"} == 0
        for: 5m
      - alert: CableModemPollStale
        expr: time() - cablemodem_last_success_timestamp_seconds > 300 or cablemodem_up == 0
        for: 5m
```

### Grafana

`cablemodem-dashboard.json` is generated by `make_dashboard.py`. It has `$DS`, `$job` and
`$instance` variables (one modem at a time), so it can be imported through the UI or provisioned:

```bash
sudo install -d -o root -g grafana -m 0755 /var/lib/grafana/dashboards/cablemodem
sudo install -o root -g grafana -m 0644 cablemodem-dashboard.json /var/lib/grafana/dashboards/cablemodem/
sudo install -o root -g grafana -m 0640 grafana-provider.yaml /etc/grafana/provisioning/dashboards/cablemodem.yaml
sudo systemctl restart grafana-server   # first time only; later file changes are picked up automatically
```

Graphs of events and errors show rates; totals ("in range") come from one `increase()` over the
selected range, never from summing graph points, which would count each event once per rolling
window it falls in. Like any `increase()`, they're estimates from counter samples. Reboots are
marked during the modem's first 10 minutes of uptime, which works however long it was offline.

The **Modem event log** table needs `CM_EXPORT_EVENT_MESSAGES=true`. The **Lock changes**
annotation (CM-STATUS messages) is off by default because a flapping channel produces hundreds a
day; switch it on from the dashboard's annotation toggles.

## Configuration

Environment variables, normally set in `/etc/cablemodem-exporter/env` (see
`cablemodem-exporter.env.example`). That file is read by systemd for the exporter and by
`cablemodem-reboot` directly, so it is limited to plain `KEY=value` lines that both read the same
way: no quotes or backslashes (`cablemodem-reboot` rejects them). Put a password that needs them in
its own file and set `CM_PASSWORD_FILE`.

| Variable | Default | Description |
|----------|---------|-------------|
| `CM_PASSWORD` / `CM_PASSWORD_FILE` | required | Web UI password, or a file containing it |
| `CM_HOST` | `192.168.100.1` | Modem address |
| `CM_USERNAME` | `cusadmin` | Web UI user |
| `CM_TIMEOUT` | `10` | Seconds the modem may stay silent during one request (an inactivity limit, not a deadline for a whole poll) |
| `CM_POLL_INTERVAL` | `30` | Seconds between polls; keep it short enough that the modem's session stays alive |
| `CM_LISTEN_ADDRESS` | `127.0.0.1` | Metrics listen address; use `0.0.0.0` only behind access controls |
| `CM_LISTEN_PORT` | `9884` | Metrics port |
| `CM_STATE_DIR` | `$STATE_DIRECTORY` or `/var/lib/cablemodem` | Where the event log copy is kept |
| `CM_EVENT_TIMEZONE` | `UTC` | Time zone of event log timestamps (IANA name) |
| `CM_EXPORT_EVENT_MESSAGES` | `false` | Export raw event log lines as metrics (see below) |

## Rebooting the modem

The modem occasionally hangs. `cablemodem-reboot` reboots it the same way as the web UI's
**Restart** button, using the same settings file as the exporter:

```bash
sudo /opt/cablemodem-exporter/venv/bin/cablemodem-reboot          # shows the modem, asks first
sudo /opt/cablemodem-exporter/venv/bin/cablemodem-reboot --yes --wait
```

`--wait` checks every 15 s, reusing one session so it doesn't fill the modem's log with logins, and
succeeds only when the modem is OPERATIONAL **and** has provably booted again. Each status reading
gives a window for when the modem booted (uptime is in whole seconds and was read at some point
during the request), and the earliest possible new boot must be later than the latest possible boot
from the reading taken just before rebooting. Being reachable or having a small uptime isn't taken
as proof, and readings that can't tell the two boots apart count as "no restart seen".

If no restart is confirmed within `--wait-timeout` (default 600 s, validated before anything is
sent), it exits with code 2. The deadline caps each request's timeout, but that is an inactivity
limit like `CM_TIMEOUT`: a modem that keeps trickling data, or retries after a dropped connection,
can keep the command running past the deadline. A result that arrives late is never reported as
success.

**It can't factory-reset the modem.** On the CD8000 the Restart button sends setter `fun=8` and
"RESET TO FACTORY SETTINGS" sends `fun=7` (`common_page/RgConfig.html`). Before rebooting, the tool
downloads that page from the modem itself and refuses unless the Restart button's handler sends
`fun=8` and the factory reset button's sends something else, so firmware that renumbered its
functions can't turn a reboot into a reset. The client has no way to send any other action.

## Metrics

All metrics are declared in one table, `METRICS`, at the top of `cablemodem_exporter.py`. Each poll
builds a complete snapshot of samples and publishes it in one step, so a scrape always sees exactly
one poll and nothing lingers from an earlier one: values the modem reports as missing or
non-numeric (e.g. `N/A`) are absent rather than 0, and after a failed poll (or before the first)
only the exporter's own metrics are present.

| Metric | Labels | Description |
|--------|--------|-------------|
| `cablemodem_up` | | 1 if the last poll of the modem succeeded |
| `cablemodem_last_success_timestamp_seconds` | | Time of the last successful poll |
| `cablemodem_poll_duration_seconds` | | Duration of the last poll |
| `cablemodem_poll_errors_total` | `kind` | Failed polls: `auth`, `protocol`, `transport` or `internal` |
| `cablemodem_exporter_logins_total` | | Logins made by the exporter; should stay flat |
| `cablemodem_exporter_build_info` | `version` | Exporter version |

### Event log

| Metric | Labels | Description |
|--------|--------|-------------|
| `cablemodem_events_total` | `category` | New log entries seen |
| `cablemodem_events_by_priority_total` | `priority` | New log entries seen |
| `cablemodem_cm_status_events_total` | `code`, `description`, `channel_id` | DOCSIS CM-STATUS messages, decoded |
| `cablemodem_last_event_timestamp_seconds` | `category` | Time of the newest event seen |
| `cablemodem_event_log_entries` | `priority` | Lines currently in the modem's log (0 for absent priorities) |
| `cablemodem_event_log_entry_timestamp_seconds` | `time`, `priority`, `category`, `message` | **Opt-in**: one series per log line (see below) |

Event categories are a fixed list (`cm_status`, `gui_login`, `reboot`, `t3_timeout`, `mdd_lost`,
…, `other`), priorities are the syslog names plus `other`, and CM-STATUS codes and channels are
limited to 2 and 3 digits, so label sets stay bounded whatever the firmware logs. Category,
priority and error-kind counters start at 0. CM-STATUS combinations are created when first seen,
so as usual with Prometheus, `increase()` can't see a combination's very first occurrence.

`CM_EXPORT_EVENT_MESSAGES=true` adds one series per distinct log line (value = event time), which
the dashboard's event log table shows. Its cardinality grows with every event seen and is bounded
only by Prometheus retention; a modem with a flapping channel logs hundreds of lines a day.

### CM-STATUS codes

`description` comes from the DOCSIS CM-STATUS event type table (codes 1–11 and 16–27; 12–15 are
reserved) as implemented by Wireshark's DOCSIS dissector (`symbol_cm_status_event_vals` in
`epan/dissectors/packet-docsis-macmgmt.c`), which follows the CableLabs MULPI specification. Newer
DOCSIS revisions may add codes; anything unknown is reported as `code N` rather than dropped.

## Event log

New entries in the modem's ~20-line log are written to the exporter's stderr at their syslog
priority (`<4>` for warning, etc.), so under systemd they land in the journal with the right
level, and journald handles retention and rotation:

```bash
journalctl -u cablemodem-exporter -g '^modem event'          # modem events only
journalctl -u cablemodem-exporter -p warning                 # warnings and worse (modem + exporter)
```

Caveats:

- **Best effort.** New entries are found by comparing each copy of the log with the previous
  one. Entries that scroll out between two polls are never seen, and identical lines (same time,
  priority and text) that replace each other can't be told apart.
- **Restarts.** The previous copy is saved in the state directory, so a restart doesn't report
  the same entries again. If saving fails (logged as an error), a restart may repeat them.
- **Timestamps** are assumed to be UTC (`CM_EVENT_TIMEZONE`). On the CD8000 the modem's
  `CurrentTime` and login event times matched the HTTP `Date` header in GMT. Entries logged before
  the modem sets its clock are dated 1970 and get no timestamp.
- **Counters** start at 0 when the exporter starts; they count events seen by this process.

## How the modem is read

The web UI POSTs a `fun` code to `/xml/getter.xml` (reads) or `/xml/setter.xml` (actions), with
the current `sessionToken` cookie as the first form field. The modem rotates the token on every
response and drops requests without browser-like headers. Login is setter `fun=15` and returns
`successful;SID=<n>`; an expired session gets an empty body or the HTML index page.

**Every login is written to the modem's event log**, which only holds ~20 lines, so the exporter
keeps one session alive and only logs in again when the modem stops returning XML. Logging into
the web UI yourself may cost the exporter one more login.

`fun` codes on CD8000-7.13.198.12-NOSH, from the UI's JavaScript and a read-only scan of getter
codes 1–20:

| fun | getter.xml (read) | setter.xml (action, as used by the UI) |
|----:|-------------------|-----------------------------------------|
| 1  | `GlobalSettings`: access level, firmware, operator ids (unused) | |
| 2  | `cm_system_info`: model, firmware, serial, uptime, status | |
| 3  | `multilang`: UI languages (unused) | |
| 4  | *invalid operation* | set UI language |
| 5  | `status`: cm_status only, a subset of 2 (unused) | |
| 6  | `upstreamOFDMA_table` | |
| 7  | *invalid operation* | **RESET TO FACTORY SETTINGS** (never sent) |
| 8  | *invalid operation* | Restart (`cablemodem-reboot`) |
| 9  | `downstreamOFDM_table` | |
| 10 | `downstream_table` (SC-QAM: freq, power, SNR, modulation, channel id) | |
| 11 | `upstream_table` (ATDMA: freq, power, symbol rate in Msym/s, width) | |
| 12 | HTML index page: not a getter | |
| 13 | `eventlog_table` (~20 entries, FIFO) | |
| 14 | *invalid operation* | not used by the UI; unknown, never sent |
| 15 | HTML index page | login (`Username`, `Password`) |
| 16 | *invalid operation* | logout |
| 17 | *invalid operation* | not used by the UI; unknown, never sent |

"Invalid operation" from the getter means the code is a setter function. Setters 14 and 17 were
not probed because an unknown action could change the modem's configuration. This firmware
exposes no codeword/FEC error counters.

## Development

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -e '.[test]'
ruff check .
pytest
python make_dashboard.py > cablemodem-dashboard.json   # after editing make_dashboard.py
```

| File | Purpose |
|------|---------|
| `cablemodem_client.py` | Session handling, login, reads, and the guarded reboot; shared by both tools |
| `cablemodem_exporter.py` | The `METRICS` table, parsing, the `Exporter` (polling and its snapshot), event log |
| `cablemodem_reboot.py` | The `cablemodem-reboot` command |
| `make_dashboard.py` | Generates `cablemodem-dashboard.json` |

Tests run against sanitized responses captured from a real modem (`tests/fixtures`, including
its settings page) and a fake modem HTTP server that reproduces token rotation, login, session
expiry and setter actions; `--wait` is tested against a virtual clock. Each test builds its own
`Exporter`, so nothing is shared between tests. The source release (`python -m build --sdist`)
includes the tests, fixtures, dashboard and deployment files, and CI runs the tests from it.

## Contributing

Issues and pull requests are welcome. Please include tests for behaviour changes, regenerate
`cablemodem-dashboard.json`, and run `ruff check` and `pytest` (CI runs both on Python 3.10–3.13
and smoke-tests the built wheel). When adding another modem's responses under `tests/fixtures`,
replace serial numbers with `GD0000000000` and MAC addresses with `00:00:00:00:00:0N`; a test
fails if anything else that looks like either is committed. Never commit your env file.

Report security issues privately, as described in [SECURITY.md](SECURITY.md).
